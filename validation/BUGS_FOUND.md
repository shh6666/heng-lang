## 逐条说明

### 1 & 2 & 3. 下标访问与赋值（最严重）

**症状**：`a[i]`、`将 v 放到 a[i]` 全部语法错误。

**根因**：VM 端 `INDEX_GET` / `INDEX_SET` 指令**早就存在**，缺的只是解析器不支持下标语法。这是「实现了一半」的典型。

**修复**：解析器后缀循环同时接受 `.` 与 `[...]`；新增 `Index` / `SetIndex` AST 节点；检查器补类型推断；编译器生成 `INDEX_GET` / `INDEX_SET`；VM 补 `INDEX_SET` 实现并顺带修了 `INDEX_GET` 的引用泄漏。

**意义**：修这一条，100 个项目里有 60 多个才写得出来。

### 4 & 5. 空容器类型推断

**症状**：
```hl
变量 结果 : 序列 数 = []      // 编译错误：序列<任意> 与 序列<数> 不符
```

**根因**：`[]` 只能推断出 `序列<任意>`，而赋值检查要求类型严格相等。

**修复**：
- 声明时若初值是空容器，采用声明的目标类型（与 Java/C# 的泛型推断一致）
- 字面量内部的空容器与兄弟元素同化（`[[1,4], [], [2]]` 能推断）

**意义**：不修这条，每个函数都写不出合法的空初值，等于语言不可用。

### 6. map_set 引用计数（段错误）

**症状**：把序列存进映射，再取出来访问 → `SIGSEGV`。

**根因**：`map_set` 不 retain 传入的值。调用方（`INDEX_SET`）随后释放自己那份引用，映射里留下悬垂指针。

**修复**：`map_set` 内部 `val_retain`，明确「映射持有该值的引用」这一所有权约定。

**意义**：这是最隐蔽的一类 bug——不崩溃在出错处，而是延迟到后面某个不相关的读取时才炸。

### 7. `说出 (a+b)*c` 解析失败（最意外）

**症状**：`说出 (1 + 2) * 3` 报「语句后需换行，遇到 `*`」。

**根因**：`说出` 支持两种写法 `说出 X` 和 `说出(X)`。遇到 `说出 (1+2)*3` 时，`(` 被误判为 `说出(...)` 的调用括号，于是只解析了 `(1+2)`，`* 3` 成了游离 token。

**修复**：括号内表达式解析后，若 `)` 之后还有运算符，说明括号属于表达式本身，回退按表达式解析。

**意义**：这个 bug 存在很久没被发现，因为示例里都写 `说出 X` 不带括号。是 100 项目验证暴露的。

### 8. 空分隔符切分

**症状**：`文字.切分("hello", "")` 返回 `["hello"]`，而非 `["h","e","l","l","o"]`。

**根因**：原实现把空分隔符当作「不切分」。

**修复**：空分隔符 = 按 UTF-8 字符切分。这是中文处理的地基——回文、词频、字符统计全靠它。

### 9 & 10. 缺失的基础函数

**整数除法**：衡语只有浮点 `/`。取位（`45/10` 要得 4 不是 4.5）无法表达，基数排序直接算错。补 `数值.整除` / `数值.取余`。

**字符码**：没有 `文字.字符码` 就无法区分不同汉字（`文字.字节数("衡")` 和 `"语"` 都是 3）。散列、字符分析全部失效。补 `文字.字符码` / `文字.由码点`。

## 对衡语的实际评价

**能承载的部分**：这 100 个项目说明衡语足以表达真实的程序结构——递归、高阶遍历、嵌套容器、状态机、解析器、业务流水线。它不是一个只能打印 Hello World 的玩具。

**暴露的短板**：
1. **解析器与 VM 不同步**——下标指令 VM 早就有了，解析器却不支持，说明两侧缺乏接口对齐的检查机制
2. **引用计数约定不清晰**——`map_set` 的 retain 责任没有文档化，才漏了
3. **标准库覆盖不足**——整数运算、字符码这类基础函数缺失，直接卡住了大量项目
4. **缺少泛型仍然带来摩擦**——容器元素类型为「任意」时，只能靠我加的「容器协变」规则放宽

## 从「修 bug」到「防 bug」：两个自检工具

13 个 bug 里有 3 个属同一类——**两侧不同步**：
- 下标指令 VM 有、解析器没有
- `MOD` 指令声明了、VM 没实现
- `PERCENT` 编号与 `EQ` 冲突

这类问题不会报错，只会静默改变语义或延迟崩溃。所以修完之后我做了两个机器自检：

### `tools/check_opcode_coverage.py`

比对三方：字节码声明的指令、VM 实现的指令、编译器实际生成的指令。

第一次运行就抓出 `MOD` 未实现、`SELECT` 未声明、`DUP`/`SWAP` 是孤儿指令。

现在结果：61 条声明、61 条实现、56 条生成，**三方对齐**。

### `tools/check_token_ids.py`

检查 Token 编号是否重复。`PERCENT = 24` 与 `EQ = 24` 冲突时，
`如果 x = 5` 被静默解析成 `x % 5`，41 个项目同时失败且无任何报错。

现在：74 个 Token，**零冲突**。

两个自检都进了测试套件（`OpcodeCoverageTests`），每次跑测试都会执行。

## 第 15 条值得单独说

这是本次验证中最凶险的一个 bug：

```hl
如果 x = 5:        # 本来是比较
  返回 真
结束
```

被解析成 `BinOp(op="%")`，因为 `%` 的 token 编号误用了 `=` 的编号。
编译器不报错，检查器只报「条件必须为真假」——根本看不出根因。

没有自检工具的话，这种 bug 会反复出现。所以最后的产出不只是 100 个能跑的程序，
还有**两个能在下次犯同样错误时立刻报警的检查器**。

**最值得做的改进**：把「VM 有指令、解析器不支持」这类不同步做成编译期的自检（比如比对指令表与语法覆盖），而不是等真实项目撞出来。→ **已实现为 `tools/check_opcode_coverage.py`。**
