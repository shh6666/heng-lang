# 超指令扩展：执行报告

> 上一轮做超指令时靠猜规律，效果不错（循环 -39%）。这一轮换了做法：
> **先统计 101 个验证项目的真实指令分布，再按数据决定做哪些。**
> 结果发现了一个比「指令融合」重要得多的问题。

## 一、成果

| 基准 | 关闭超指令 | 开启超指令 | 提升 |
|---|---|---|---|
| fib(27) 递归 | 39.65 ms | 39.55 ms | -0.3% |
| 300 万循环 | 156.49 ms | **99.68 ms** | **-36.3%** |
| 20 万数组操作 | **101.6 s** | **0.03 s** | **快 3109 倍** |
| 50 万算术循环 | 46.22 ms | **21.32 ms** | **-53.9%** |

所有基准输出完全一致，零语义变化。

## 二、做法：先统计，再优化

上次凭直觉猜测哪些指令组合值得融合。这次先把 101 个项目全部编译，统计指令分布与相邻指令对。

结果：

```
最高频指令        LOAD_LOCAL    1939 次
                 PUSH_NUM      1050 次
                 STORE_LOCAL    767 次
                 INDEX_GET      373 次

最高频相邻对      LOAD_LOCAL + LOAD_LOCAL   666
                 STORE_LOCAL + LOAD_LOCAL  475
                 LOAD_LOCAL + PUSH_NUM     333
                 LOAD_LOCAL + INDEX_GET    222
```

数据直接指向两个方向：**槽位访存**和**索引访问**。所以做了两类超指令。

## 三、真正的收获：发现 O(n²)

做完索引超指令后测 array 基准，**几乎没提升（-0.4%）**。追踪下去发现：这个基准跑了 95 秒。

根因不在优化，在 `表.追加` 的实现：

```c
Seq 表.追加(xs, v)  →  复制整个 xs，再追加一个元素返回新序列
```

`xs = 表.追加(xs, v)` 在循环里就是 **O(n²)**。20 万次追加 = 200 亿次元素拷贝。

这是「小函数引发的大问题」——单看 `表.追加` 实现完全正确，放进循环就爆炸。

### 修法：原地追加 + 别名保护

加超指令 `SLOT_APPEND_SLOT` / `SLOT_APPEND_IMM`，在 `xs = 表.追加(xs, v)` 时直接原地追加。

**但第一次实现错了**：

```hl
变量 a : 序列 数 = [1]
变量 b : 序列 数 = a        // b 与 a 是同一对象
a = 表.追加(a, 2)
说出 b                      // 期望 [1]，实际 [1, 2]  ← 被污染了
```

原地追加破坏了值语义。修法是按引用计数区分：

- `rc == 1`（独占）→ 原地追加
- `rc > 1`（有别名）→ 复制后追加

修完：语义正确，性能保持（29ms）。

**这条教训值得记：优化前先确认语义边界，否则「快」是拿错误换来的。**

## 四、逐项说明

### 索引访问超指令

| 指令 | 作用 | 替代的序列 |
|---|---|---|
| `SLOT_INDEX_SLOT` | 压入 `c[i]` | `LOAD, LOAD, INDEX_GET` |
| `SLOT_INDEX_IMM` | 压入 `c[常量]` | `LOAD, PUSH, INDEX_GET` |
| `SLOT_INDEX_STORE` | `c[i] = v` | `LOAD×3, INDEX_SET` |

只在**容器静态类型是序列**时启用。文本和映射的取下标语义不同，不能合并。

### 算术超指令

| 指令 | 语义 |
|---|---|
| `SUB/MUL/DIV/MOD_SLOT_IMM` | `x = x OP 常量` |
| `SUB/MUL_SLOT_SLOT` | `x = x OP y` |
| `GT/LE/GE/EQ/NE_SLOT_IMM` | 压入 `x OP 常量` |

arith 基准提升 53.9%，说明纯算术循环受栈往返影响最大。

### 追加超指令（最大收益）

| 指令 | 语义 |
|---|---|
| `SLOT_APPEND_SLOT` | `xs = 表.追加(xs, v)`（v 是变量） |
| `SLOT_APPEND_IMM` | `xs = 表.追加(xs, 常量)` |

这是本轮唯一一个**改变复杂度**的优化，其余都是常数因子。

## 五、调试开关

加了 `HENG_NO_SUPER=1` 环境变量，可关闭全部超指令融合。

用途：
- 精确测量每条优化的收益（就是上面那些对照数据）
- 排查「开了优化才出错」的问题时，快速定位

这比维护两份代码可靠得多。

## 六、过程问题

### 自检工具没能拦住生成错误

批量生成 11 条 C 实现时，脚本参数顺序写错，把十六进制编号当成语句插入了代码：

```c
int idx2 = g_fbase[g_frame_top-1] + s2;
    217                        ← 应该是 L[idx2].u.num -= imm2;
break;
```

**`check_opcode_coverage.py` 报告「三方一致」**——它只比对名字，不检查 C 语法。是 clang 报的错。

教训：静态自检能覆盖「有没有」，覆盖不了「对不对」。C 编译本身才是最可靠的门槛。

### 编号冲突再现

`SLOT_APPEND_SLOT` 的枚举定义漏加（只加了 OPERANDS 引用），导致 `AttributeError`。这次是 Python 导入期直接崩溃，好定位。

## 八、下一步

**已经做完的**：槽位算术、索引读写、原地追加、比较。

**还能做但收益递减**：

- `LOAD_LOCAL + PUSH_NUM` 融合（333 次）——但要占用 12 字节操作数，收益可能被解码开销吃掉
- 字符串驻留——短文本去重，降低分配开销
- 更多设置超指令组合——按数据看，剩下的大多是低频组合

**关键判断**：本轮最大的收益来自**修复杂度**（O(n²) → O(n)），不是来自加指令。这提示下一步应该先做一次**复杂度审计**——把所有标准库函数过一遍，看有没有类似 `表.追加` 的隐藏平方行为。这比继续加超指令更有价值。

按这个判断，我建议下一步做「标准库复杂度审计」，而不是继续堆指令。
