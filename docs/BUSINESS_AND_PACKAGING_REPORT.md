### 开发过程中修复的语言缺陷

写这 100 个项目的过程本身就在发现问题：

**1. 序列赋值是引用共享，不是值语义（严重）**

```hl
变量 a : 序列 文本 = ["x", "y"]
变量 b : 序列 文本 = a
将 "z" 放到 b[0]
说出 a      // 期望 [x, y]，实际 [z, y]
```

这把衡语「值语义」的卖点打破了。修法：`SLOT_INDEX_STORE` 加写时复制（rc > 1 时先复制）。

**2. 记录字段赋值从未实现**

```hl
将 5 放到 r.n     // 语法错误
```

`FIELD_GET` 一直有，`FIELD_SET` 从来没写。补了指令 + AST + 解析器。

**3. 单字母大写记录名被泛型规则误判（回归）**

上一轮加泛型时按「单字母大写」判断类型变量，把 `记录 R` 全废了。改成只认显式声明在 `<...>` 里的名字。

**4. 无量纲字面量与带单位值比较报错**

`如果 数量 <= 10` 其中 `数量是 数<个>`，报量纲不匹配。允许一侧无量纲。

**5. 单位表只有 9 个单位**

写医疗用例时 `数 公斤` 直接语法错误。扩到 70+ 个业务常用单位（公斤、毫克、元/人、件/箱…）。

**6. 关键字不能作变量名**

`变量 数 : 数 = 5` 报语法错误。`数` 是业务高频变量名（数量）。让 `数`/`文本` 在名字位置可用。

### 一个反向验证：量纲系统是对的

写医疗剂量时：

```hl
变量 体重 : 数 公斤 = 60<公斤>
变量 每公斤 : 数 毫克/公斤 = 5<毫克/公斤>
体重 * 每公斤      // 300毫克，单位正确约掉
```

一度以为 `10 × 100元/个` 得出 `元/个` 是 bug，其实**编译器是对的**——无量纲 × 元/个 = 元/个。我该写 `数量 : 数 个`。

**是我的用例写错，不是语言错。**

## 三、编译器功能调研

实测 rustc 1.95 与 clang，对比出三档差距：

### 差距最大：诊断质量

clang：
```
/tmp/e.c:1:18: error: expected expression
    1 | int main(){int x=;}
      |                  ^
```

衡语（改造前）：
```
编译/运行错误：4:6 类型错误：未定义变量 undefined_var
```

按此调研结果，本轮实现了：

**诊断带源码上下文**（编译期与运行期都有）：

```
bad.hng:4:6: 错误[E01]: 未定义变量 undefined_var
  |
4 |   说出 undefined_var
  |        ^^^^^^^^^^^^^
  |
  帮助: 检查变量名是否拼错；局部变量需要先「变量 名字 : 类型 = 值」声明
```

运行时错误也带源码行——这需要 VM 输出 `@pc` 偏移，再由编译期的 PC→行号表映射回源码行。

**警告系统**（三条，宁少勿滥）：

```
w1.hng:2:3: 警告[W01]: 变量 没用 声明后未使用
  |
2 |   变量 没用 : 数 = 5
  |     ^^
```

`-W01` 未使用变量 / `-W02` 不可达代码 / `-W03` 映射键重复。支持 `-Werror`。

跑 300 个项目：**零警告**（说明规则不滥报）。

### 命令行

补齐主流编译器的基础选项：

```
-o <路径>        指定输出
-O0..-O3         优化级别（-O0 关闭超指令便于调试）
-w / -Werror     警告控制
--build / --run  产物与运行分离
-V / -h          版本与帮助
```

### 明确不做

交叉编译、包管理器、增量编译、DWARF 调试信息。理由见 `docs/COMPILER_FEATURE_RESEARCH.md`。

## 四、macOS 打包

### 产物

```
dist/henger    9.2 MB 单文件可执行（Python 运行时 + 编译器 + 原生 VM 全在里面）
```

关键决策：**必须随包带上编译好的 VM 二进制**。原先 `ensure_native()` 会现场用 clang 编译，但目标机器不一定装了编译器。

VM 查找顺序：`HENG_VM` 环境变量 → 包内 `heng2/bin/hengvm` → 源码树 → `PATH`。

### 安装

```sh
python3 tools/build_macos.py
PREFIX=~/.local ./install.sh
```

安装脚本会去掉 macOS 的 quarantine 属性（否则 Gatekeeper 会拦）。

自检：打包后自动跑一个最小程序验证输出为 `3`。

### 写工具时暴露的 4 个缺陷

这是本轮最重要的产出——**算法题（前 200 个项目）一个都没撞出来**：

**1. 长表达式不能换行**

```hl
x = 甲 + 乙
  + 丙        // 语法错误
```

中大型项目只能把长表达式硬写成一行，无法维护。修法：词法层在 `(` `[` `{` 内丢弃换行。

**2. 没有命令行参数能力**

工具没法接受输入。补 `系统.参数()` 与 `系统.脚本目录()`。

**3. 文件 IO 是桩实现**

```c
} else if (strcmp(name, "文件.写入") == 0) {
    char c[1024]; snprintf(c, sizeof c, "写入:%s", target);   // 根本没写文件
```

调用成功、返回「完成」，但文件是空的。补真实读写。

**4. `文字.合并` 用 512 字节缓冲中转**

```c
char b[512]; to_text(items[i], b, sizeof b);   // 元素一长就截断
```

截断点常落在中文字符中间，写出的文件不是合法 UTF-8。ASan 查不出来（不是越界，是逻辑截断），靠 `file` 命令发现编码非法才定位到。

报表里一行几十个汉字就会踩到。

## 七、六个缺陷的分布说明了什么

本轮共修复 6 个语言缺陷，分布很有规律：

- **算法类项目（前 200 个）**：0 个新缺陷
- **业务类项目（新增 100 个）**：6 个新缺陷
- **写真实工具（3 个）**：4 个新缺陷（与前 6 个部分重叠）

**结论清楚：验证项目的「形态」比「数量」重要。**

算法题都是短函数、纯计算、无 IO。真实工具是长文件、多模块、有输入输出、有持久化。后者才能撞出前者撞不到的问题。

**下一步建议**：继续写真实工具，而不是继续加项目。
每写一个工具，平均能发现 1-2 个之前没暴露的缺陷。
