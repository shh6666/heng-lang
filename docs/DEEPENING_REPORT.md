## 二、标准库复杂度审计

### 做法：实测而非读代码

`表.追加` 的教训是：单看实现完全正确，放进循环就是 O(n²)。读代码抓不到这类问题。

所以写了 `tools/audit_stdlib_complexity.py`：对每个函数喂 4 倍递增的输入，按耗时比判定复杂度（4x → O(n)，16x → O(n²)）。

关键细节：**要扣除进程启动开销**（约 3.7ms），否则小规模的固定成本会掩盖真实差异。

### 发现的问题

| 函数 | 问题 | 8000 规模耗时 | 修复后 |
|---|---|---|---|
| `表.排序` | 插入排序，O(n²) | 197 ms | **<1 ms** |
| `表.去重` | 嵌套循环比较，O(n²) | 68 ms | **2 ms** |
| `字典.写入` | 线性扫描找键，O(n²) | 134 ms | **4 ms** |
| `表.连接`（累加） | 每次整表复制，O(n²) | 125 ms | **<1 ms** |

### 修复方式

**映射加哈希索引**——原本注释写着「AI 场景的键通常很少」，100 项目验证推翻了这个假设。加了 FNV-1a 哈希 + 链式桶，写入从 O(n) 降到 O(1)。

**排序换 qsort**——原本是插入排序。`val_cmp` 恰好满足严格弱序，可以直接喂 `qsort`。一行改动，快一个数量级。

**去重改用哈希集**——元素先转文本作键，整体 O(n)。

**连接加超指令**——`acc = 表.连接(acc, [x])` 单元素字面量直接退化为原地追加。

### 一个覆盖面缺口

审计中发现 `表.追加(xs, f(x))` 这种**参数是表达式**的写法不触发超指令，仍走 O(n²)。补了 `SLOT_APPEND_STACK`（求值压栈后原地追加）。

修完后审计全绿，并已加入测试套件（`ComplexityAuditTests`）。

## 三、字符串驻留

短文本（≤24 字节）在进程内共享同一对象。

| 指标 | 关闭驻留 | 开启驻留 | 变化 |
|---|---|---|---|
| 20 万次重复文本耗时 | 23 ms | **14 ms** | **-39%** |
| 峰值内存 | 31.1 MB | **6.6 MB** | **-79%** |

**内存才是主收益**。速度提升有限，因为测试里主要开销是循环本身。

实现要点：驻留对象 `rc` 不参与回收（由进程持有），`obj_release` 遇到 `interned` 标志直接返回。

## 四、闭包：这次做成了

上一轮我主动放弃了闭包，理由是三种方案都不可靠。这一轮换了思路，成功了。

### 方案：闭包对象携带捕获值

- `T_FUNC` 值指向 `Obj`，其中 `len` 存函数索引，`items/n` 存捕获值数组
- 创建时（`MAKE_CLOSURE`）按序从栈上取外层值，**按值复制**
- 调用时（`CALL_VALUE`）把捕获值放进帧尾，体内用 `LOAD_FREE i` 读取

### 按值捕获是刻意的

```hl
变量 n : 数 = 1
变量 f = 做法(x : 数) -> 数 => x + n
n = 100
说出 f(5)      // 6，不是 105
```

捕获是创建时的**快照**。这避免了悬垂引用，也与「并发任务不共享可变状态」一致。

### 过程中踩的坑

**union 误读导致段错误**：`T_FUNC` 曾用 `u.num` 存索引，闭包用 `u.obj` 存对象。两者在 union 里冲突，把数值当地址解引用就崩了。

修复：统一表示——**无捕获的函数也包成闭包对象**（`ncap=0`），`CALL_VALUE` 只处理一种形态。

**高阶函数不带捕获**：`表.映射(xs, 闭包)` 最初输出 `[0,0,0]`，因为 `HIGHER_ORDER` 里 `fnv.u.num` 又踩了同一个坑。修完并给 `call_fn_sync_ex` 加捕获参数。

现在 `表.映射`/`表.过滤`/`表.折叠` 都支持闭包：

```hl
变量 倍 : 数 = 3
表.映射([1,2,3], 做法(x : 数) -> 数 => x * 倍)    // [3, 6, 9]
```

## 五、JIT：技术上成了，实用上有限

### 实测数据

| 方式 | 1000 万次自增循环 |
|---|---|
| 衡语解释器 | 32.55 ns/次 |
| 衡语 JIT | **2.56 ns/次** |
| C | 0.83 ns/次 |

JIT 比解释器快 **12.7 倍**，接近 C。

### 方案

`heng2/jit.py`：字节码 → C 源码 → clang 编译成动态库 → `ctypes` 加载调用。

只处理**纯数值槽位的循环**（无函数调用、无对象操作）。遇到不确定的指令就放弃，退回解释执行。

用法：`python3 -m heng2.jit <文件.hng>`

### 但覆盖率只有 2%

在 200 个项目上测：**只有 2 个能 JIT**。

原因很实在——统计 148 个循环的阻碍因素：

| 阻碍指令 | 出现次数 |
|---|---|
| `INDEX_GET` / `SLOT_INDEX_*` | 465 |
| `CALL_STD` | 112 |
| `JMP_IF` | 57 |
| `LEN` | 53 |

真实代码的循环体几乎都含**数组下标**和**函数调用**。要覆盖这些，得把完整的运行时对象模型搬进 JIT——那等于重写 VM。

**结论：JIT 原型有价值（证明了可行性、给出了速度上限），但在当前代码形态下覆盖率太低，不值得投入完整实现。**

### 新暴露的缺陷

**1. 记录字段赋值完全没实现**

```hl
将 5 放到 r.n      // 语法错误
```

`FIELD_GET` 一直有，`FIELD_SET` 从来没写过。101 个项目里没撞到，因为它们多用不可变记录。

补了 `FIELD_SET` 指令 + `SetField` AST + 解析器路径。

**2. 单字母大写记录名被泛型规则误判（回归）**

```hl
定义 记录 R:
  字段 n : 数
结束
变量 r : R = R(1)    // 类型错误：R 与 R 不符
```

上一轮加泛型时，我按「单字母大写」判断类型变量，把 `R`、`T` 这类记录名全废了。

修复：只有**显式声明在 `<...>` 里**的名字才是类型变量。

**3. 无量纲字面量与带单位值比较报错**

```hl
如果 数量 <= 10:      // 数量是 数<个>，报量纲不匹配
```

修复：一侧无量纲时允许比较，与赋值的放宽规则一致。

### 量纲系统的一个正面验证

写阶梯定价时我一度以为是缺陷：

```hl
变量 数量 : 数 = 10
变量 单价 : 数 元/个 = 100<元/个>
数量 * 单价            // 得出 元/个，报错
```

看起来不对，但**编译器是对的**：无量纲 × 元/个 = 元/个。我该写 `数量 : 数 个`。

改成 `10<个> × 100<元/个> = 1000元`，单位正确约掉。**量纲系统工作完全正确，是我的用例写错了。**

## 八、对下一阶段的判断

这轮五项工作，价值排序：

**1. 复杂度审计（最高）** — 一个 `表.追加` 值 3109 倍。而且它建成了自动检查，以后新函数都会被审。

**2. 闭包（次高）** — 上一轮放弃是对的（三种方案都不可靠），这一轮换思路成功。lambda 现在真正可用了。

**3. 200 项目验证（高）** — 暴露了字段赋值、类型变量误判两个真实缺陷。新增的 99 个项目偏业务场景，比算法更能撞出问题。

**4. 字符串驻留（中）** — 内存收益明确（-79%），速度提升有限。

**5. JIT（低，但有价值）** — 技术上证明可行（12 倍），实测覆盖率只有 2%。投入产出比不成立，但这份数据本身避免了盲目投入。

**下一步建议**：继续扩验证项目，而不是加优化。K 类（业务系统）一上来就撞出两个缺陷，说明真实场景的代码形态与算法题差别很大。**每加 50 个业务项目，大概能撞出 1-2 个之前没发现的编译器缺陷**——这比优化性能更值得做。
