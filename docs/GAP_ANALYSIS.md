# 衡语与主流语言：差距评估与优化方向

> 本文基于衡语内核 v2 的实测数据与逐项语法核对，给出四件事的结论：
> 原生 VM 与主流编译器的差距、衡语与主流语言的差距、优缺点、优化方向。

## 一、结论摘要

| 维度 | 结论 |
|---|---|
| 原生 VM 定位 | 属于「字节码虚拟机」这一档，比 CPython 快 3–5 倍，与 V8 各有胜负，比编译型语言慢 9–19 倍 |
| 语法完备性 | **基本够用，但不齐全**。核心控制流/函数/错误/并发齐全，缺泛型、模式匹配、lambda、接口 |
| 最大优势 | 量纲系统、能力沙箱、契约，这三项是主流语言**没有**的语言级保证 |
| 最大短板 | 生态为零、无泛型导致容器不可复用、无 JIT 导致循环慢 |
| 最该做的事 | 不是 AOT，而是补泛型与下标访问这两项「语言完整性」缺口 |

## 二、原生 VM 与主流编译器的差距

### 2.1 实测数据

同一份工作负载在五种实现上的耗时（取 5 次最优值，含进程启动）：

| 实现 | fib(27) | 300 万次循环 | 执行模型 |
|---|---|---|---|
| C（clang -O2） | 4.7 ms | 8.6 ms | 编译为机器码 |
| **衡语原生 VM** | **41.8 ms** | **166.2 ms** | 字节码解释 |
| Node.js（V8） | 56.2 ms | 60.4 ms | 字节码 + JIT |
| Python 3 | 235.4 ms | 434.4 ms | 字节码解释 |

### 2.2 三项解读

**第一，衡语已经越过 CPython。** 递归调用快 5.6 倍，循环快 2.6 倍。这不是调优的胜利，而是架构差异：CPython 每步要处理对象引用计数、类型分派、GIL，而衡语的指令序列直接把操作映射到 f64 与栈操作。

**第二，衡语和 V8 各有胜负，但性质不同。** fib 上衡语更快（41.8 vs 56.2 ms），因为 V8 的启动与编译开销在小程序里摊不开。但循环上 V8 快 2.7 倍——这是 JIT 把循环热点的类型检查、边界检查全部消除之后的差距，是**架构性**的。

**第三，与 C 的 9–19 倍差距是这类架构的固有成本。** 每一轮循环衡语都要做：取操作码、解码操作数、switch 分派、操作数栈读写。这几步在原生机器码里完全不存在。

### 2.3 差距清单（按影响排序）

| 差距 | 主流做法 | 衡语现状 | 性能影响 |
|---|---|---|---|
| **无 JIT** | 热点方法编译为机器码（V8、HotSpot、LuaJIT） | 纯解释执行 | 循环慢 2–3 倍 |
| **无内联缓存** | 缓存「类型 → 方法」映射（V8、Self） | 每次操作码都走 switch | 间接调用慢 |
| **无逃逸分析** | 栈上分配短命对象，消除引用计数 | 全部堆分配 + 引用计数 | 分配开销高 |
| **无寄存器分配** | 值放寄存器而非内存栈 | 全部经操作数栈中转 | 访存次数多 |
| **无常量折叠跨过程** | 编译期算完整个表达式树 | 仅单指令级 | 常量表达式未优化 |
| **字节码未做类型特化** | 为「数 + 数」生成专用指令 | 通用 ADD 运行时判型 | 每步多一次分支 |

**没有第 6 项是当前最容易补的**：为数值运算加 `ADD_NUM` 之类的特化指令，能省掉热路径上的类型判断，预计提升 15–25%，工作量却只有 JIT 的十分之一。

## 三、衡语与主流语言的差距

### 3.1 语法完备性逐项核对

实测 29 项语言特性（真编译真运行，不是查文档）：

| 类别 | 特性 | 衡语 | 主流语言对照 |
|---|---|---|---|
| **基础** | 变量/常量、赋值 | ✓ | 全部支持 |
| | if/else、循环、重复 N 次 | ✓ | 全部支持 |
| | 遍历序列 | ✓ | 全部支持 |
| | 序列与映射字面量 | ✓ | 全部支持 |
| **函数** | 定义、调用、递归、默认参数 | ✓ | 全部支持 |
| | 泛型 | ✗ | Rust/Go/TS/C#/Java 支持 |
| | lambda / 匿名函数 | ✗ | 全部现代语言支持 |
| **复合** | record、字段访问 | ✓ | 全部支持 |
| | 映射**下标访问** | ✗ | 全部支持 |
| | 解构赋值 | ✗ | Python/JS/Rust 支持 |
| **控制** | `匹配`（模式匹配） | ✗ | Rust/Swift/Scala 支持 |
| | `当`（while 关键字） | ✗ | 全部支持 |
| **错误** | try/catch/finally | ✓ | 全部支持 |
| | 错误签名（可能生） | ✓ | Java checked exception 类似 |
| **抽象** | 接口 / trait | ✗ | Rust/Go/Java/C# 支持 |
| | 类 / 继承 | ✗ | Java/C++/Python 支持 |
| **类型** | 可选类型（`数?`） | ✗ | Rust/Kotlin/Swift/TS 支持 |
| **文本** | 字符串插值 | ✗ | Python/JS/Kotlin 支持 |
| **独特** | 量纲系统 | ✓ | **无主流语言支持** |
| | 能力沙箱（指令级强制） | ✓ | **无主流语言支持** |
| | 契约（要求/保证） | ✓ | Eiffel 有，主流无 |
| | 真并发（禁写外层） | ✓ | Go 有 goroutine 但可写共享内存 |
| | FFI（直连 C 库） | ✓ | 全部支持 |

### 3.2 语法是否齐全：不齐全，但缺口不算致命

**已齐的部分**（撑起一个可用语言的最小集合）：变量、控制流、函数、复合类型、错误处理、并发、模块、FFI。

这已经足够写出 `examples/` 里那 20 个真实程序，包括投放分析器、AI agent 闭环、并发统计。这是**能用的语言**，不是玩具。

**缺的部分，按修复优先级**：

1. **映射下标访问 `m["a"]`** —— 最刺眼的缺陷。映射字面量支持，取值却不支持，必须用 `字典.取值(m, "a")`。这是不一致，零学习成本却能立刻修好，优先级最高。
2. **泛型** —— 长期影响最大。没有泛型，`表.排序` 只能返回 `序列 任意`，用户拿回来都要强转。这直接限制了标准库的可用性。
3. **lambda** —— 影响表达力。没有 lambda，`表.过滤` 这类高阶函数无法写出，只能靠循环手写。
4. **接口/trait** —— 影响架构。但衡语定位是编排层，这一项可以长期不做。
5. **模式匹配** —— 影响可读性，不是必需。

## 四、优缺点

### 4.1 优势：三项主流语言没有的东西

**量纲系统**是最大的差异化。`消耗 : 数 元` 除以 `线索 : 数 个` 得到 `数 元/个`，编译器自动算维度向量，乘错量纲（元 × 元）直接编译期报错。这个能力在投放分析场景里极其贴合——单位错配是这类业务最隐蔽的 bug。主流语言一个都没有（F# 有 units of measure，但生态极小）。

**能力沙箱做成指令**。`CAP_CHECK` 由虚拟机在指令边界强制，不存在「某处忘了检查」的可能。旧实现出过一次真实绕过（`_expr_name` 对 Call 返回 None，检查永不触发），新架构从根上消除了这类问题。

**契约内建**。`要求:` / `保证:` 写在函数签名里，编译器生成检查代码。比单元测试更细粒度，比注释可靠。

### 4.2 劣势：三个结构性短板

**生态为零**。这是最硬的差距，也是短期内无法弥补的。主流语言的价值有一半在库，衡语目前 54 个标准库函数 + FFI 直连 C 库，做业务系统远远不够。

**无泛型导致抽象能力受限**。标准库返回 `序列 任意`，用户每次取值都面临类型不确定。这在写复杂程序时会持续产生摩擦。

**无 JIT 导致计算密集型任务吃亏**。循环慢 V8 2.7 倍，意味着衡语不适合做数据处理的主力。

## 五、优化方向

按「收益 ÷ 成本」排序，前四项都不需要 AOT。

### 第一梯队：立刻做，成本低收益明确

**1. 修映射下标访问**

```hl
变量 价格 = 单价表["抖音"]     // 现在不支持，只能用 字典.取值(...)
```

这是语言一致性问题，不是新特性。改动集中在解析器与 `INDEX_GET` 指令，一两天可完成。

**2. 数值运算特化指令**

为热路径加 `ADD_NUM` / `LT_NUM` / `MUL_NUM`，省掉每次的操作数类型判断。预计提速 15–25%，工作量远小于 JIT。

**3. 字节码层面的常量折叠**

`81000 / 1800` 这类编译期可算的表达式，现在每次运行都算一遍。折叠后直接产出一个 `PUSH_NUM`。

### 第二梯队：值得做，决定语言上限

**4. 泛型（约束形式）**

不需要完整的类型系统，只要能表达「序列的元素类型」。这一项做完，标准库的返回类型才能精确，用户不必强转。

**5. lambda 表达式**

配合 `表.过滤` / `表.映射` 这类高阶函数，表达力会有质的变化。

### 第三梯队：审慎评估

**6. JIT 编译**

能把循环性能拉到接近 C，但工作量是整个后端的两三倍，且引入平台依赖（ARM64/x86 各一套）。**只有当衡语开始跑计算密集任务时才值得做。**

**7. AOT 编译**

如前述，当前收益低。`hengvm` 只有 36KB，可移植性优势明显，AOT 换机器码的代价不值得。

### 不建议做

- **垃圾回收**：引用计数在 AI 编排场景（对象少、生命周期短）足够，GC 会引入停顿与复杂度过高的问题。
- **类继承**：与衡语的记录 + 接口路线冲突，且组合优于继承已是共识。

## 六、定位判断

衡语不是「更快的 Python」，也不是「中文版 C++」。它的准确定位是：

> **面向 AI 编排与业务数据处理的中文语言，靠量纲安全与能力沙箱建立差异，靠 FFI 借用 C 生态补齐能力。**

这个定位下：
- 性能不是核心指标（AI 场景 99% 时间在等网络与推理）；
- 生态可以靠 FFI 借（Math/压缩/加密都能直连 C 库）；
- 语法要够用但不能臃肿（泛型与 lambda 值得补，类继承不值得）。

按这个判断，最该投入的是**语言完整性**（下标、泛型、lambda），而不是**执行性能**（JIT、AOT）。
