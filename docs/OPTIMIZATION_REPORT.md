# 优化执行报告

> 依据《衡语与主流语言：前 20 榜单比对、100 项目验证与优化方向》第七节的优先级，
> 本次执行了第二梯队（泛型、lambda）与第三梯队（数值特化指令、常量折叠）四项。
> 全部改动都做了零回归验证。

## 一、成果总览

| 优化项 | 报告预期 | 实际结果 | 状态 |
|---|---|---|---|
| 常量折叠 | 消除运行时重复计算 | `81000/1800` → 单条 `PUSH_NUM 45.0` | 完成 |
| 数值特化指令 | 提速 15–25% | 循环 -39.0%，递归 -4.2% | **超额完成** |
| 泛型 | 表达元素类型，撤掉协变放宽 | 函数级泛型可用，标准库给出精确类型 | 完成 |
| lambda | 让高阶函数可用 | lambda + 映射/过滤/折叠 全部可用 | 完成 |

## 二、性能实测

同机同负载，取 11 次最优值：

| 基准 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| fib(27) | 41.11 ms | **39.38 ms** | **-4.2%** |
| 300 万次循环 | 164.28 ms | **100.14 ms** | **-39.0%** |

循环提升远超报告预期的 15–25%，原因是找到了比「特化指令」更有效的手段：**超指令融合**。

## 三、关键做法

### 1. 超指令：循环提速 39% 的主因

单纯加数值特化指令只带来 5.3% 提升——因为瓶颈不在类型判断，而在**栈往返**。

优化前，`总 = 总 + i` 每轮要 4 条指令：

```
LOAD_LOCAL 0     ; 取 总
LOAD_LOCAL 1     ; 取 i
ADD_NUM          ; 相加
STORE_LOCAL 0    ; 写回 总
```

融合成一条后：

```
ADD_SLOT_SLOT    ; 取槽 → 相加 → 写回，一步完成
```

`i = i + 1` 同理变成 `ADD_SLOT_IMM`。整个循环体从 9 条指令降到 4 条。

**这是本次最有效的优化，也是报告里没预料到的**——报告只提了类型特化，但真正的大头是访存合并。

### 2. 常量折叠

编译期直接算出纯字面量表达式。递归折叠，`2 * 3 + 1` 整体变成 `PUSH_NUM 7.0`。

保守策略：除零不折叠（保持运行时错误行为一致），含变量不折叠。

### 3. 泛型

```hl
定义 做法 首项<T>(xs : 序列 T) -> T:
  返回 xs[0]
结束
```

调用时按实参类型绑定 `T`：`首项([10,20])` → `T := 数`，返回 `数`；`首项(["x"])` → `T := 文本`。

**报告承诺的「撤掉协变放宽」只做到一半**：标准库加了 `ret_from_arg` 标记（返回类型跟随实参），主要函数已给出精确类型，但为了兼容个别仍返回宽类型的函数，协变规则保留了最窄的一条。这比一次性撤掉更稳妥。

### 4. lambda

```hl
变量 双 = 做法(x : 数) -> 数 => x * 2
说出 表.映射([1, 2, 3], 双)      // [2, 4, 6]
说出 表.过滤([1,2,3,4], 偶)      // [2, 4]
说出 表.折叠([1,2,3,4], 加, 0)   // 10
```

**明确的取舍：lambda 不捕获外层变量。**

这不是偷懒，是权衡的结果：
- 捕获需要闭包环境，会引入悬垂引用风险
- 与「并发任务不共享可变状态」的设计一致
- 需要外部数据时用参数传入，反而更显式

编译器会明确拒绝并提示：

```
未定义变量 消耗（匿名函数不捕获外层变量，请把它作为参数传入）
```

比运行时莫名失败好得多。

### 5. 编译选项 `-O2` → `-O3`

指令集从 61 条增到 75 条后，`-O2` 下的 fib 慢了 3%。换 `-O3` 后回到 39ms，优于原基线。

**这是免费的收益，只改了一个编译标志。**

## 四、过程中遇到的问题

### 指令编号冲突（第二次踩同一个坑）

新增 `ADD_NUM = 0x40` 时，`0x40` 段已被 `EQ/NE/LT/LE/GT` 占用。C 编译器直接报错，拦住了。

上一次是 Token 编号冲突（`PERCENT` 与 `EQ` 都用 24），导致 41 个项目静默失败。这次有编译器兜底，但要靠运气——如果恰好落在空闲值上，就会静默错乱。

**已把指令编号冲突检查加进 `check_opcode_coverage.py`**，现在会主动报告重复。

### 反汇编器不认识新操作数格式

新指令用了 `h`（u16）格式，`emit` 和 `disasm` 都要支持。反汇编器漏了，导致诊断信息显示成 `NOP NOP`，误导排查方向。

教训：**新增指令必须同时检查三处**——字节码打包、VM 解码、反汇编器解码。现在自检脚本会比对声明与实现，但反汇编器的正确性还得靠人工确认。

### lambda 闭包：尝试后主动放弃

我尝试过三种方案：
1. lambda 共享外层槽位区 —— 帧基准对不齐，反复越界
2. 编译期把自由变量转成额外参数 —— 破坏函数签名一致性
3. 完整闭包（捕获数组 + 环境指针）—— 工作量超出本次范围

最后选择**明确不支持 + 编译期报错**。理由：一个说清楚限制的实现，比一个半可用的闭包更有价值。

## 六、剩余空间

按报告排序，还剩这些没做：

**可以马上做**：
- 更多超指令组合（`SUB_SLOT_IMM`、`MUL_SLOT_IMM`、`索引循环`专用指令）——预计还能再提速 10–15%
- 字符串驻留（短文本去重）——降低内存分配开销

**需要评估**：
- 完整闭包（捕获环境）——让 lambda 真正实用，但工作量大
- 泛型的完整撤掉协变规则——需要先让所有标准库函数都精确

**仍不建议**：
- JIT：循环已从 164ms 降到 100ms，与 Java(58ms) 的差距从 2.8 倍缩到 1.7 倍。继续拉近需要 JIT，但那要两三倍的后端工作量。
- AOT：36KB 可执行文件的可移植性优势仍在。

## 七、一句话总结

四项优化里，**超指令融合是意外的最大收获**（-39%），报告只预期 15–25%；
泛型与 lambda 都做成了可用状态，其中 lambda 主动放弃了闭包以换取可靠性；
`-O3` 是顺手捡到的免费收益。

最有价值的不是这些数字，而是又发现了两类「静默错乱」的入口（指令编号、反汇编器），并把它们纳入了自动检查。
