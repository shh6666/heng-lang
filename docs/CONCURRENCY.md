# 衡语并发模型（内核 v2）

> 本文定义衡语的并发语义。设计目标：**多线程真并行，且在语言层面杜绝数据竞争**。

## 一、核心决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 调度 | 多线程真并行 | 工具调用是等待型 IO，真并行才能让 N 个调用同时等在途 |
| 让出时机 | 等待型操作自动让出 | 用户不用写 await，语义自然 |
| 共享状态 | **默认禁止写外层变量** | 从语言层面消除数据竞争，而不是靠用户自律 |
| 内存 | **每任务独立堆 + 跨任务传值拷贝** | 无锁、无竞态；代价是跨任务传对象要拷贝 |
| 显式等待 | 新增 `等待完成` | 既保留自动汇总，又允许精确控制 |

## 二、任务模型

```
任务（Task）= 一次独立的字节码执行
  ├─ 自己的代码指针 pc
  ├─ 自己的值栈（独立分配，不与父任务共享）
  ├─ 自己的帧栈
  ├─ 自己的局部槽位区
  ├─ 自己的堆（文本/序列/映射/记录都分配在这里）
  ├─ 自己的能力白名单（继承父任务，可再收窄）
  └─ 一个信箱（任务结束时的返回值写入这里）
```

**关键不变量**：任务之间不共享任何可变状态。跨任务只有两条通路：

1. 发起时传入的参数（**深拷贝**进子任务堆）
2. 任务结束时的返回值（**深拷贝**回父任务堆）

这两条通路都是「传值」，所以不存在两个线程同时读写同一块内存的可能。

## 三、并发语句的语义

### 3.1 `发起 做法(参数…)`

在**新线程**上启动 `做法`。

- 实参在**当前任务**求值，然后深拷贝给子任务；
- 立即返回，不等待子任务完成；
- 子任务结束时，返回值深拷贝回父任务，写入信箱 `<做法名>_信箱`；
- 父任务可以在任意时刻 `接收(<做法名>_信箱)` 取结果。

### 3.2 `接收(信箱) 为 变量`

取信箱里的结果。

- 若子任务**已完成**：立即取到值，阻塞时间为 0；
- 若子任务**未完成**：当前任务阻塞等待（**让出线程**，不空转）；
- 若同一做法发起过多次：按完成顺序排队，先进先出。

### 3.3 `同时 … 结束`

一个并发作用域。

- 块内所有 `发起` 的任务同时运行；
- **块结束时自动汇总**：等待块内所有任务完成（隐式 join），保证不泄漏线程；
- 若块内有任务失败，按顺序把第一个错误抛给父任务，其余任务的结果丢弃。

### 3.4 `等待完成 做法(参数…)`

新增语法。发起并**立即等待**该任务结束，返回值直接作为表达式的值。

```hl
变量 成本 = 等待完成 求成本(消耗, 线索)
```

等价于 `发起` + `接收` 两步合一，但不需要命名信箱。适用于「我就要这个结果，不想管调度」。

区别：

| 写法 | 用途 |
|---|---|
| `发起 f(…)` + `接收(f_信箱) 为 x` | 多个任务并行，稍后逐个取 |
| `等待完成 f(…)` | 只要一个结果，写起来最简 |

## 四、禁止写外层变量

### 4.1 规则

任务（包括并发块内的代码）**只能读**外层变量，**不能写**。

```hl
开始:
  变量 总计 : 数 = 0
  同时:
    发起 累加(1)        // 内部若写 总计 → 编译期报错
  结束
  总计 = 总计 + 1        // 主任务自己写，允许
结束
```

### 4.2 为什么能这么做

因为真正的并发算法本来就该用消息传递，而不是共享内存累加。禁止写外层后：

- 不存在「两个任务同时 `总计 = 总计 + 1` 丢失更新」；
- 不需要用户理解锁、原子操作、内存序；
- 编译器能静态证明无竞态。

### 4.3 需要汇总时怎么办

用返回值：

```hl
同时:
  发起 统计(甲)
  发起 统计(乙)
结束
接收(统计_信箱) 为 甲结果
接收(统计_信箱) 为 乙结果
变量 合计 = 甲结果 + 乙结果
```

先并行计算，再在父任务里串行汇总。这是标准做法，也是最不容易出错的。

## 五、内存与回收

每个任务持有独立的堆。回收策略：

- 任务结束时，整个堆一次性释放（不用逐个引用计数）；
- 任务运行期间的临时对象用引用计数回收，但**计数器不跨线程**，所以无需原子操作；
- 跨任务传递时深拷贝，所以对象的归属永远明确。

这样做的代价是「传大对象要拷贝」。但对衡语的目标场景（AI 编排、业务数据处理），传的都是小结构（几 KB 的结果、几十条记录），拷贝成本远低于加锁。

## 六、指令集

```
SPAWN  <u16 函数索引> <u8 实参数>     创建任务
RECV   <u16 目标槽位>                 取信箱（空则阻塞）
JOIN   <u16 任务组 id>                等待组内全部完成
AWAIT  <u16 函数索引> <u8 实参数> <u16 目标槽位>   等待完成（合成一条指令）
```

任务组 id 由编译器在编译 `同时` 块时分配，保证块结束时精确 join 本块发起的任务。

## 七、与旧实现的关系

旧实现的「并发」是同步执行（`发起` 立即跑完），只有输出恰好相同。新实现是真并行。

**为了保持 19 个示例输出不变**：

- `同时` 块仍隐式 join，所以块内任务必然在块结束时完成；
- 若块内任务不涉及耗时操作，输出顺序仍由 `接收` 的显式顺序决定，与旧实现一致；
- 只有当任务真的耗时时，才会看到「总耗时 = 最慢那个」的差别——这正是我们要的。

## 八、验收标准

1. **真并行可证**：3 个各耗时 100ms 的工具调用并行，总耗时 < 200ms（而非 ≈300ms）。
2. **无竞态**：构造尝试写外层变量的程序，必须编译期报错。
3. **无泄漏**：`同时` 块结束必定 join，不残留线程。
4. **结果一致**：19 个示例输出与旧实现逐字节相同。
5. **错误传递**：子任务抛错，父任务能收到，且已启动的其他任务被正确回收。
