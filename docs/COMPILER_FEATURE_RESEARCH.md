# 主流编译器功能调研与衡语差距

> 方法：以本机实际安装的 rustc 1.95.0、clang（Apple）为基准，逐项实测其 CLI 与诊断行为，
> 与衡语 v2.0.0 对照。不做二手资料转述，每条差距都附实测输出。

## 一、主流编译器的功能构成

### 1.1 命令行接口（CLI）

| 功能 | rustc | clang | 衡语当前 |
|---|---|---|---|
| 指定输出路径 | `-o <file>` | `-o <file>` | ✗ |
| 输出目录 | `--out-dir` | ✗ | ✗ |
| 优化级别 | `-O` / `-C opt-level=` | `-O0..-O3` | ✗（固定 -O3）|
| 生成产物的类型 | `--emit=mir,llvm-ir,asm,obj,link` | `-S` / `-c` / `-E` | ✗ |
| 打印中间信息 | `--print=crate-name,cfg,…` | `-###` / `-dumpversion` | `--disasm`（仅汇编）|
| 目标平台 | `--target <triple>` | `--target=<triple>` | ✗（仅本机）|
| 库搜索路径 | `-L` / `-l` | `-L` / `-l` | ✗ |
| 版本与详细版本 | `-V` / `-vV` | `--version` | `--version`（简版）|
| 详细模式 | `-v` | `-v` | ✗ |
| 错误说明查询 | `--explain E0308` | 文档 | ✗ |

**观察**：主流编译器的 CLI 都有清晰的「输入 → 中间产物 → 输出」三段式，
并且几乎都支持 `-o` 与优化级别控制。衡语目前只能「编译并运行」，没有产物概念。

### 1.2 诊断质量（差距最大的地方）

clang 实测输出：

```
/tmp/e.c:1:18: error: expected expression
    1 | int main(){int x=;}
      |                  ^
1 error generated.
```

要素拆解：
1. **文件:行:列** 定位
2. **严重级别**（error / warning / note）
3. **源码行** + 行号
4. **插入符**精确指向出错位置
5. **末尾统计**（N errors generated）

衡语实测输出：

```
编译/运行错误：4:6 类型错误：未定义变量 undefined_var
```

差距：
- ✗ 没有源码行
- ✗ 没有位置指示符
- ✗ 没有修复建议
- ✗ 没有 warning 级别（只有 error）
- ✗ 没有「相关位置」（如变量在此处定义）

rustc 更进一步：每个错误带**代码编号**（E0308）、**多位置标注**、**修复建议（help:）**。

```
error[E0308]: mismatched types
 --> src/main.rs:2:9
  |
2 |     let x: i32 = "hello";
  |            ^^^   ^^^^^^^ expected `i32`, found `&str`
  |
help: consider changing the type annotation
```

### 1.3 警告系统

| 能力 | rustc | clang | 衡语 |
|---|---|---|---|
| 分级控制 | `-A/-W/-D/-F <lint>` | `-Werror` 等 | ✗ |
| 列出所有警告 | `-W help` | `-Weverything` | ✗ |
| 单条抑制 | `#[allow(...)]` | `#pragma` | ✗ |

**观察**：没有警告系统，意味着「能跑但有隐患」的代码无法提示。
比如衡语里 `变量 未使用 = 1` 完全不报。

### 1.4 增量与缓存

| 能力 | rustc | clang | 衡语 |
|---|---|---|---|
| 增量编译 | `-C incremental=<dir>` | ✗（靠外部）| ✗ |
| 依赖追踪 | 内建 | 靠 make/ninja | ✗ |
| 编译缓存 | sccache 生态 | ccache 生态 | ✗ |

**观察**：衡语单文件编译只有 30ms 左右，增量需求不紧迫。
但 JIT 的 C 缓存（`/tmp/heng_jit`）已经有雏形。

### 1.5 工具链与包管理

| 工具 | Rust | Go | Python | 衡语 |
|---|---|---|---|---|
| 包管理 | cargo | go mod | pip | ✗ |
| 格式化 | rustfmt | gofmt | black | ✗ |
| 静态检查 | clippy | vet | mypy | 部分（类型检查内建）|
| 文档生成 | rustdoc | godoc | sphinx | ✗ |
| 测试框架 | cargo test | go test | pytest | 自制 unittest 脚本 |
| 调试信息 | `-g` + lldb/gdb | ✓ | ✓ | ✗ |

## 二、衡语最该补的三件事（按投入产出排序）

### 第一优先：诊断带源码上下文

**现状**：
```
编译/运行错误：4:6 类型错误：未定义变量 undefined_var
```

**目标**：
```
错误[E01]: 未定义变量 undefined_var
  位于 bad.hng:4:6
    |
  4 |   说出 undefined_var
    |        ^^^^^^^^^^^^^ 这里用了未定义的变量
    |
  帮助: 是否想用 `x`？
```

**为什么最优先**：衡语的目标用户是中文业务人员，不是专业程序员。
他们看不懂「4:6」但一定看得懂带箭头的源码行。

**工作量**：中等。只需在读源码时保留行文本，报错时格式化输出。

### 第二优先：警告级别

**当前完全没有**。至少需要三条：
1. 未使用的变量
2. 不可达的代码（`返回` 之后还有语句）
3. 重复的映射键字面量

**为什么**：这三条都是「业务人员常犯但不会立刻出错」的问题。

### 第三优先：命令行 `-o` 与产物概念

**现状**：只能编译并运行，没有「产出可执行文件」的概念。

**目标**：
```
henger app.hng -o app.hbc      # 编译产物
henger --run app.hbc           # 运行产物
henger -O0 app.hng             # 关优化（调试用）
```

**为什么**：这是「编译器」变成「产品」的门槛。

## 三、暂不追的功能（明确不做）

| 功能 | 不做的理由 |
|---|---|
| 多目标平台交叉编译 | 衡语定位是业务脚本，不是系统编程 |
| 包管理器 | 单文件语言，暂无模块生态需求 |
| 增量编译 | 编译只要 30ms，收益不明显 |
| 调试信息（DWARF） | 先做源码级诊断，比行号调试更实用 |
| Lint 规则体系 | 先做 3 条核心警告，不铺开 |

## 四、结论

主流编译器的竞争力不在「能编译」，而在：

1. **诊断质量**——clang 的波浪线、rustc 的 E 码与修复建议
2. **产物控制**——`-o`、优化级别、中间产物
3. **工程化配套**——包管理、格式化、测试、调试

衡语作为面向业务人员的中文语言，**诊断质量是第一竞争力**，
其次是能被当作独立产品使用的 CLI。

这两项是下一阶段的重点。
