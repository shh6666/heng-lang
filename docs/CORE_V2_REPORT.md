# 衡语内核 v2 实施报告

> 面向的问题：旧实现是「中文语法 + Python 求值器」，本质上是一层转译，不是独立语言。
> 本报告记录新内核的架构、实施结果与验证数据。

## 一、问题定性

旧实现的执行路径是：

```
.hng 源码 → 词法 → 语法 → AST → Python 递归求值（isinstance 分派 + dict 查找）
```

执行阶段完全依赖 Python 运行时。后果不是「慢一点」，而是结构性的：

| 指标 | 旧实现 | 说明 |
|---|---|---|
| fib(25) | 1180 ms | 每步都是 Python 函数调用 + 字典哈希 + 类型分派 |
| 语义天花板 | Python 运行时 | 量纲、能力都只能在外层「加检查」，无法成为语言本身的一部分 |
| 分发形态 | 必须带 Python | 无法产出独立可执行产物 |

## 二、新架构

```
.hng → 词法(heng2/lexer2) → 语法(parser2) → 检查(check2) → 代码生成(compiler2)
                                                                    ↓
                                                            .hbc 字节码（自足二进制）
                                                                    ↓
                                                                    │
                                                        原生 C VM (native/hengvm.c)
                                                        唯一执行引擎，独立可执行
```

关键分界：**`.hbc` 不包含任何 Python 对象引用**。它可写盘、可跨进程加载、可由 C 写的 VM 执行。

## 三、指令集

栈式、定长操作码 + 变长操作数，共 47 条指令，九组：

| 组 | 指令 |
|---|---|
| 常量与栈 | `PUSH_NUM` `PUSH_CONST` `PUSH_NIL` `PUSH_TRUE` `PUSH_FALSE` `POP` `DUP` `SWAP` |
| 变量 | `LOAD_LOCAL` `STORE_LOCAL` `LOAD_GLOBAL` `STORE_GLOBAL` |
| 算术 | `ADD` `SUB` `MUL` `DIV` `MOD` `NEG` `CONCAT` |
| 比较 | `EQ` `NE` `LT` `LE` `GT` `GE` `NOT` |
| 控制流 | `JMP` `JMP_IF` `JMP_IFNOT` |
| 函数 | `CALL` `RET` `RET_NIL` |
| 集合 | `MAKE_SEQ` `MAKE_MAP` `MAKE_REC` `FIELD_GET` `INDEX_GET` `INDEX_SET` `LEN` |
| 输出与错误 | `PRINT` `THROW` `TRY_BEGIN` `TRY_END` `END_TRY` |
| 能力与调用 | `CAP_CHECK` `SANDBOX_ENTER` `SANDBOX_EXIT` `AUTHORIZE` `BUILTIN` `CALL_STD` `CALL_HOST` `CALL_TOOL` |
| 终止 | `HALT` |

## 四、量纲：编译期消除，运行期零成本

这是新内核相对旧实现的**结构性优势**。

旧实现把单位挂在运行期值上，每次加减乘除都要算维度向量。新实现：

1. 检查层为每个数值表达式算维度向量（长度/时间/质量/金额/计数/温度）；
2. 不匹配直接编译期报错，**不生成任何字节码**；
3. 生成代码时丢弃单位，只保留 f64 运算；
4. 单位仅作为**显示信息**，编码在 `PRINT` 指令的操作数里。

验证：带单位与不带单位的同构程序，指令序列完全一致，只差 `PRINT` 的单位串。

## 五、能力：指令级不可绕过

旧实现的能力检查是运行期 `caps` 集合判断，曾出过一次真实绕过（`_expr_name` 对 Call 返回 None，检查永不触发）。

新实现把它做成指令：

```
CAP_CHECK <能力名池索引>
```

由 VM 在指令边界强制执行。任何调用路径，只要经过 `CAP_CHECK`，都没有「某处忘了检查」的可能。

## 六、内存模型

C VM 用引用计数：

```
Obj = { kind, rc, text/len | items/n | keys/vals/n }
```

`val_retain` / `val_release` 在指令级精确控制。文本、序列、映射、记录都是堆对象。

## 七、实测数据

同一段递归 fib（纯函数调用 + 分支 + 算术）：

| 实现 | fib(25) | 相对旧实现 |
|---|---|---|
| 旧实现（中文语法 + Python 求值器） | 1180 ms | 基准 |
| 新内核 · Python VM（自有字节码） | 644 ms | ×1.8 |
| **新内核 · 原生 C VM（自有字节码）** | **11.9 ms** | **×99** |

注：11.9 ms 含进程启动与文件读取。100 万次循环负载：0.04 s。

字节码体积：fib 程序 156 字节。

## 八、语义等价验证

19 个示例程序，新内核输出与旧实现**逐字节一致**，包括错误消息：

```
一致 19/19
```

测试套件：

| 套件 | 数量 | 结果 |
|---|---|---|
| 新内核（tests/test_heng2.py） | 34 | 全部通过 |
| 旧实现（tests/test_heng.py） | 102 | 全部通过（未破坏原有实现） |

新内核测试包含**原生 VM 与 Python VM 的交叉验证**：同一个 `.hbc`，两边执行结果必须完全相同。这条测试抓出了三个真实缺陷：

1. `BUILTIN` 指令格式定义与 C 端读取不一致（少读 1 字节，导致指令流错位）
2. 入口帧 `slot_top` 从 0 开始，第一次 `CALL` 覆盖了入口变量
3. `sp` 处理不当导致递归时调用者的中间结果丢失

## 九、实施中修复的真实缺陷

除上述三个，还有：

| 缺陷 | 现象 | 根因 |
|---|---|---|
| 赋值被解析成比较 | `i = i + 1` 静默失效，循环不终止 | 表达式里 `=` 兼作相等，先解析表达式会吃掉赋值 |
| `finally` 不执行 | 资源清理逻辑丢失 | 正常路径直接跳过 finally 段 |
| 能力调用参数丢失 | `工具.查询("x")` 得到 `查询(空)` | 能力分支未推断实参，参数变量槽位未回填 |
| 遍历变量类型丢失 | `"前缀" + 项` 运行期类型错误 | 迭代变量未登记元素类型 |
| 标准库返回序列类型过粗 | 元素拼接被静态拒绝 | 返回 `序列<任意>` 而非 `序列<文本>` |
| 全局常量未初始化 | 函数内读常量为空 | 常量求值未生成到入口 |
| 输出单位错位 | 文本输出拿到数值的单位 | 单位按 PRINT 顺序对位，分支下必然错乱 |

最后一条的修复方式是**把单位编码进 `PRINT` 指令**，彻底消除顺序依赖。

## 十、架构自检

测试中固化了三条结构性断言，防止实现退化回转译层：

1. Python 侧不存在解释执行器（`heng2/vm.py` 必须不存在）
2. 编译器前端（`compiler2` / `check2` / `api2`）不含 `eval` / `exec` / 解释循环
3. `.hbc` 必须能写盘后由独立进程加载执行，结果一致

## 十一、与旧实现的分工

- `heng/`（旧实现）**保留不动**，作为语义参考与对照基线。102 项测试仍全部通过。
- `heng2/` + `native/` 是新内核，`python3 -m heng2 <文件.hng>` 使用。

## 十二、已知边界

1. **并发**是单线程同步语义：`发起` 立即执行并把结果存入信箱。协作式调度尚未实现。
2. **原生 VM 的标准库**已覆盖完整（54 项），不再有「请改用 --py-vm」的分支。
3. **FFI** 在原生 VM 中通过 `CALL_HOST` 可达，但需要 Python 宿主，属于混合模式。

## 十三、下一步

按用户确认的优先级：**AOT 编译到 ARM64 机器码**。

理由：当前 11.9 ms 已经是「VM 分派」的天花板。再往上只有一条路——跳过字节码，直接生成机器码。目标是让 fib 这类纯计算达到 C 的量级（亚毫秒）。

同时保留 `.hbc` 作为中间产物，AOT 编译器读 `.hbc` 生成汇编，复用现有前端与检查层。
