## 三、性能实测：衡语在前 20 中的位置

同机同负载，取 5 次最优值（含进程启动）：

| 语言 | fib(27) | 300 万次循环 | 执行模型 |
|---|---|---|---|
| C | 4.5 ms | 8.9 ms | 机器码 |
| C++ | 4.4 ms | 8.9 ms | 机器码 |
| Rust | 5.2 ms | 9.2 ms | 机器码 |
| Swift | 7.4 ms | 10.4 ms | 机器码 |
| **衡语** | **47.5 ms** | **190.2 ms** | **字节码解释** |
| Java | 54.2 ms | 58.6 ms | 字节码 + JIT |
| Node (V8) | 56.7 ms | 60.1 ms | 字节码 + JIT |
| PHP 8.4 | 117.7 ms | 128.8 ms | 字节码 + JIT |
| Ruby 2.6 | 136.9 ms | 283.6 ms | 解释 |
| Python 3.13 | 235.0 ms | 439.0 ms | 字节码解释 |

### 三项判断

**第一，衡语已进入「前 20 的前半段」。** 在 10 种实测语言中，衡语的递归性能排第 5（仅次于四种编译型语言），循环性能排第 6（被 Java 与 V8 的 JIT 超过）。

**第二，与编译型的差距是 9–19 倍，与 JIT 型的差距在 1–3 倍内。** 这个分布正是「纯解释字节码」的典型位置。衡语尚未做任何针对性优化——没有类型特化指令、没有内联缓存、没有常量折叠。

**第三，最有意义的对照是 Java 与 V8。** 它们与衡语同为字节码，但多了 JIT。递归上衡语更快（JIT 预热摊不开），循环上慢 2.7–3.2 倍（JIT 把类型检查全消掉了）。这说明：**衡语当前的短板不在架构选错，而在没做热路径优化。**

### 衡语独有的三项

把矩阵按「有没有」筛一遍，衡语有三项是 20 种语言都没有的：

1. **量纲系统**——编译器计算维度向量，单位错了编译期报错。F# 有 units of measure 但不在前 20。
2. **能力沙箱做成指令**——权限检查由虚拟机在指令边界强制，不存在「某处忘了查」。20 种语言里没有一个是语言级的。
3. **契约内建**（要求/保证）——Eiffel 有，但不在前 20。

这三项是衡语的真实差异化，也是它唯一有理由存在的论证。

## 五、语法完备性：46 项核心特性核对

逐项真编译真运行核对，不是查文档：

| 类别 | 已支持（40 项） | 缺失（6 项 + 5 项设计取舍） |
|---|---|---|
| 基础 | 变量、常量、赋值、四种基本类型 | — |
| 控制 | if/else、循环、重复 N 次、遍历、逻辑组合 | **模式匹配**、while 关键字（用「循环 条件」代替） |
| 函数 | 定义、调用、递归、默认参数、错误签名 | **泛型**、**lambda** |
| 复合 | 记录、序列、映射、**下标读写**、**链式下标** | 解构赋值 |
| 错误 | try/catch/finally、错误签名、契约 | — |
| 并发 | 同时/发起/接收/等待完成、禁写外层 | — |
| 权限 | 沙箱、授权、执行、观察 | — |
| 类型 | 量纲、可选单位、强类型推断 | 可选类型（`数?`） |
| 文本 | 拼接、切分、合并、替换、按字符切分、字符码 | **字符串插值** |
| 抽象 | 记录 + 接口路线 | **接口/trait**、类继承（不做） |
| 互操作 | 模块导入、FFI 直连 C 库 | — |

**结论**：补完下标访问后，衡语从「写不出循环里的数组操作」变成「能写完整程序」。46 项里支持 40 项，剩下的 6 项中，泛型与 lambda 影响最大，模式匹配与字符串插值影响体验，接口与可选类型可以长期不做。

**是否齐全的判断**：够写算法、数据结构、业务流水线、解析器。不够写大型框架（无泛型/接口）、不够写函数式风格（无 lambda）。

## 六、优缺点

这一节把优势与劣势分开看，不混在一起下笼统结论。

### 优势

按差异化程度排序，下面三项是 20 种主流语言里没有的。

**差异化明确**：量纲 + 能力沙箱 + 契约，这三项直接对应「AI 编排 + 业务数据」场景的痛点。投放分析里单位错配、agent 越权调用、输入输出契约不清，都是真实会发生的事故。

**性能已越过 Python**：递归快 5 倍、循环快 2.3 倍。对编排类应用（99% 时间在等网络）完全够用。

**架构干净**：字节码 + 原生 VM，无 AST 解释、无宿主语言依赖、36 KB 可执行文件。这一点比很多同类项目扎实。

**验证出的健壮性**：100 个真实程序跑下来，修掉 13 个 bug 后全部通过，说明基础不是纸糊的。

### 劣势

下面三项是结构性问题，其中生态一项短期无法解决。

**生态为零**：这是最硬的。54+ 标准库函数加 FFI，做业务系统远远不够。

**无泛型带来持续摩擦**：`表.排序` 返回 `序列 任意`，每个使用者都要面对类型不确定。我只能加「容器协变」规则来放宽，这是权宜之计。

**解析器与 VM 不同步**：下标指令 VM 早就有，解析器却不支持。100 项目验证直接撞出这个问题，说明缺乏两侧接口的自动对齐检查。

**无 JIT**：循环落后 Java/V8 约 3 倍。计算密集场景吃亏。

## 七、优化方向（按 100 项目验证的实际反馈排序）

排序依据不是理论收益，而是 100 个项目验证时真实卡住的地方。

### 第一梯队：验证过程中直接卡住的

**1. 已完成：下标访问与赋值**——这是最大的阻塞项，已修（含链式下标、负下标、引用泄漏）。

**2. 已完成：基础函数补全**——整数除法、取余、字符码、按字符切分。这四项不补，半数项目写不出来。

**3. 已完成：指令与 Token 的自动自检**——这是本次验证最重要的产出。三个缺陷属同一类：
指令声明了但 VM 没实现（`MOD`）、VM 实现了但语法不支持（下标）、Token 编号冲突（`%` 与 `=` 都是 24）。

这类问题**不报错，只静默改变语义**，只能靠机器兜。已建两个检查器：
- `check_opcode_coverage.py`：比对「字节码声明 / VM 实现 / 编译器生成」三方，当前 61/61/56 对齐
- `check_token_ids.py`：检查 Token 编号重复，当前 74 个零冲突

两者都进了测试套件，每次跑测试自动执行。

### 第二梯队：影响语言上限

**4. 泛型**——不需要完整类型系统，只要能表达「序列的元素类型」。做完后标准库能给出精确返回类型，我加的协变放宽规则可以撤掉。

**5. lambda**——`表.过滤`、`表.映射` 这类高阶函数的前提。做完表达力会有质变，100 个项目里多个可以少写一半代码。

### 第三梯队：性能

**6. 数值运算特化指令**——`ADD_NUM`、`MUL_NUM`、`LT_NUM`，省掉热路径的类型判断。预计提速 15–25%，工作量远小于 JIT。这是把循环性能从 190ms 向 150ms 推的最省力方式。

**7. 常量折叠**——`81000/1800` 这类编译期可算的表达式现在每次都算。

**8. JIT**——能把循环拉到接近 C，但工作量是整个后端两三倍，还要 ARM64/x86 各一套。只有当衡语开始跑计算密集任务时才值得。

**9. AOT**——仍不建议。36 KB 可执行文件的可移植性优势，比机器码的速度更有价值。

### 不建议做

- **垃圾回收**：引用计数在编排场景够用，GC 引入停顿与复杂度
- **类继承**：与「记录 + 接口」路线冲突，组合优于继承已是共识
- **字符串插值**：优先级低于 lambda，且现有拼接足够

## 八、总体判断

衡语经 100 个项目验证后，可以给一个更实在的评价：

**它是一个真实可用的语言，但还不完整。**

- 能写：算法、数据结构、业务处理、解析器、状态机——这 100 个项目就是证据
- 不能写：大型框架、函数式风格、计算密集型任务
- 独特价值：量纲安全与能力沙箱，这两项 20 种主流语言都没有

**最该做的不是加性能，是补完整性。** 100 个项目里没有一个是卡在「不够快」上，全部卡在「写不出来」——下标、空容器、整数除法、字符码。这清楚说明当前瓶颈是语言表达力，不是执行效率。

按这个判断，泛型与 lambda 的优先级应高于 JIT 与 AOT，而「解析器与 VM 的指令覆盖自检」应该立刻加——它能在下一个 bug 变成阻塞之前发现它。
